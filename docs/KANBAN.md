## 1. Как устроена доска (колонки)

На скриншоте шаблон GitHub Projects «Backlog / Ready / In progress / In review / Done». Для одного разработчика
(и для проекта с чёткой последовательностью фаз) этот набор **оптимален — не добавляйте лишних колонок**.
Рекомендую оставить эти 5 и при желании добавить шестую — **Blocked**.

| Колонка | Для чего | Что сюда попадает | Правило входа | Лимит (WIP) |
|---|---|---|---|---|
| **Backlog** | Вся будущая работа проекта. «Склад» идей и задач. | Все карточки T001…T139 при первоначальной загрузке | Любая задача, даже сырая | нет |
| **Ready** | Задачи, которые можно взять **прямо сейчас**, без вопросов. | Карточки текущей фазы, у которых выполнены зависимости и ясны критерии приёмки | Выполнен *Definition of Ready* (п. 4.1) | **5–7** (запас на 1–2 недели) |
| **In progress** | То, над чем вы работаете сейчас. | Карточка с открытой веткой | Взята из Ready сверху вниз (по приоритету) | **1–2** (жёстко!) |
| **In review** | Код написан, идёт самопроверка/CI/ревью PR. | Карточка с открытым PR | PR создан, CI запущен | **2–3** |
| **Done** | Принято: слито в `main`, критерии выполнены. | Закрытые issues | PR смержен, чек-лист DoD выполнен | нет |
| *(опц.)* **Blocked** | Задачи, которые остановлены внешним фактором. | Ждёте решения/данных/другую задачу | В карточке написано, **чего именно** ждёте | нет |

### Почему именно так

- **Backlog ≠ Ready.** В Backlog лежат все 100+ задач. Если смотреть на них каждый день, вы утонете. Работаете только с колонкой *Ready*.
- **WIP-лимит In progress = 1–2.** Главная причина «вечных» проектов — десять начатых задач и ни одной законченной. Пока не закончите текущую, новую не берёте.
- **In review нужна даже в одиночку.** Это этап самопроверки: перечитать diff в PR, дождаться CI, проверить критерии приёмки. Половина багов находится именно здесь.
- **Done — только после слияния в `main`**, а не «вроде работает у меня».
- Блокировки (*Blocked*) делайте колонкой, а не лейблом, если они у вас частые; иначе достаточно лейбла `status:blocked`.

### Как задача путешествует по доске

```text
Backlog ──► Ready ──► In progress ──► In review ──► Done
   ▲           │            │              │
   └───────────┴────────────┴──────────────┘   (возврат, если выяснилось, что задача не готова / переработать)
```

### Рекомендуемый ритм (соло)

1. Раз в неделю (15 минут): просмотреть Backlog текущей фазы → перенести 5–7 задач в **Ready**, дописать недостающее (критерии, зависимости).
2. Каждый день: взять верхнюю из **Ready** → **In progress** → ветка `feat/T046-idm`.
3. Открыли PR (`Closes #N`) → **In review** (автоматически, см. workflows).
4. Слили → **Done** (автоматически).
5. Раз в фазу: ретроспектива (что было сложнее, чем оценивали), корректировка оценок.

## 2. Поля, представления и автоматизация GitHub Projects

### 2.1. Поля (Fields) проекта

Создайте в Projects → ⚙ Settings → Fields:

| Поле | Тип | Значения | Зачем |
|---|---|---|---|
| **Status** | Single select (есть по умолчанию) | Backlog, Ready, In progress, In review, Done (+Blocked) | Колонки доски |
| **Priority** | Single select | P0, P1, P2, P3 | Порядок взятия в работу |
| **Size** | Single select | XS, S, M, L, XL | Оценка трудоёмкости (XS ≤ 1 ч, S ≈ полдня, M 1–2 дня, L 3–5 дней, XL — разбить) |
| **Phase** | Iteration/Single select | M0 … M9 | Группировка по фазам (или используйте *Milestone*) |
| **Service** | Single select | map, simulation, gateway, infra, proto, frontend, all | Фильтрация по области |
| **Estimate** | Number | часы/дни | Уже показан на скриншоте (`Estimate: 0`) — суммируется по колонке |

> Совет: значения `Priority`, `Size` и `Service` уже заложены в **labels** карточек (раздел 3). Если загружаете issues скриптом, поля проекта проще заполнить массово во вкладке **Table** (выделить строки → вставить значения).

### 2.2. Представления (Views)

На скриншоте уже есть вкладки; рекомендую такую конфигурацию:

| View | Тип | Настройка | Зачем |
|---|---|---|---|
| **Backlog** (доска) | Board | Group by: *Status*; фильтр `milestone:@current` (опц.) | Основная рабочая доска |
| **Priority board** | Board | Group by: *Priority*; фильтр `-status:Done` | Что важнее всего |
| **Team items** → **Service** | Table | Group by: *Service*, сортировка по Priority | Срез по сервисам |
| **Roadmap** | Roadmap | Group by: *Milestone*; метки по Size | Видеть фазы на временной шкале (нужны даты/итерации) |
| **My items** → **Now** | Table | Фильтр `status:"In progress","In review","Ready"` | Только то, что в работе |
| **Blocked / Risks** (новая) | Table | Фильтр `label:status:blocked` | Что мешает двигаться |

### 2.3. Workflows (автоматизация, на скриншоте их 7)

Включите встроенные правила (Projects → ⋯ → Workflows):

| Workflow | Настройка |
|---|---|
| **Item added to project** | Status = **Backlog** |
| **Item reopened** | Status = **Backlog** (или Ready) |
| **Pull request linked to issue** | Status = **In review** |
| **Pull request merged** | Status = **Done** |
| **Item closed** | Status = **Done** |
| **Auto-add to project** | Автоматически добавлять новые issues репозитория `Fi44er/synthcity` |
| **Auto-archive items** | Архивировать закрытые > 14 дней |

> Если какого-то правила в вашей версии нет — достаточно трёх: *Item added → Backlog*, *PR merged → Done*, *Item closed → Done*.

## 4. Правила работы

### 4.1. Definition of Ready (карточка может попасть в *Ready*)

- [ ] Понятна цель, описан контекст
- [ ] Есть чек-лист «Что нужно сделать» и критерии приёмки
- [ ] Все зависимости (раздел «Зависимости» карточки) уже в *Done*
- [ ] Оценка Size ≤ **L**. Карточку **XL** сначала разбейте на подзадачи (Sub-issues / чек-лист)
- [ ] Понятно, как проверить результат (тест, метрика, ручной сценарий)

### 4.2. Definition of Done (карточка может попасть в *Done*)

- [ ] Все пункты чек-листа и критерии приёмки выполнены
- [ ] Тесты написаны и проходят (`go test -race ./...`), линтер чист
- [ ] CI зелёный, PR смержен в `main`
- [ ] Документация / `docs/` / README / proto-комментарии обновлены, если менялся контракт или поведение
- [ ] Метрики/логи добавлены, если задача затрагивает рантайм
- [ ] Нет «TODO без issue»: всё отложенное заведено отдельной карточкой

### 4.3. Git-процесс

- Ветка от `main`: `feat/T046-idm`, `fix/T002-higway-typo`, `chore/T013-remove-demo`.
- Коммиты — Conventional Commits: `feat(sim): add IDM car-following (T046)`.
- PR: заголовок = заголовок карточки, в описании `Closes #<номер issue>`; один PR — одна карточка.
- Ветка `main` защищена: только через PR, обязательные проверки CI.
- Большая карточка (L/XL) — несколько небольших PR, привязанных к одной карточке через `Part of #N`.

### 4.4. Как работать с оценками

| Size | Время | Действие |
|---|---|---|
| XS | ≤ 1 ч | Брать между делом |
| S | ≈ полдня | |
| M | 1–2 дня | Типичная карточка |
| L | 3–5 дней | Ведите по чек-листу, коммитьте часто |
| XL | > 1 недели | **Обязательно разбить** перед стартом |

Оценки приблизительные — после каждой фазы сверяйте план/факт и корректируйте следующие.

## 5. Порядок выполнения и критический путь

Фазы выполняются **по порядку**, но внутри фазы многое можно делать параллельно. Критический путь до работающей симуляции:

```text
T010 Kafka ─► T011 kafkax ─► T012 proto sim ─► T014 pkg/ ─► T020/T021 ingest ─► T022 координаты
   ─► T029 PostGIS ─► T030 GetChunks ─► T031 REST карты ─► T034 viewer           ← «карта на экране»
   ─► T032 ExportGraph ─► T040 sim каркас ─► T041 SimGraph ─► T042 часы ─► T045/T046 машины+IDM
   ─► T047 маршруты ─► T048 спавн ─► T049 snapshots ─► T050 Hub ─► T051 WS                  ← «машины едут»
   ─► T060–T062 светофоры ─► T064 дедлоки                                                    ← «город живой»
   ─► M4 управление ─► M5 спецтранспорт ─► M6 реализм ─► M7 пешеходы ─► M8 масштаб ─► M9 prod
```

**Что можно делать параллельно:** CI/DX (T016, T017) и исправление багов map-service (T002–T006, T018) — независимо от Kafka; viewer (T034) — параллельно с ядром симуляции после T031.

**Что откладывать осознанно:** шардирование (T112), социальные силы (T106), калибровка (T095), чекпоинты (T134) — приступайте, только если измерения показывают необходимость.

> Принцип: **вертикальный срез раньше горизонтального.** Как можно скорее (к концу M2) добейтесь, чтобы 100 машин ехали по реальной карте и отображались на фронте — дальше всё наращивается итеративно.

## 8. Массовое создание issues через `gh`

Вручную создавать 100+ карточек долго. Рядом лежит скрипт `create_issues.sh`, который:

1. создаёт все **labels**;
2. создаёт **milestones** (фазы M0…M9);
3. создаёт все **issues** с заголовком, описанием, labels и milestone;
4. (опционально) добавляет их в ваш **Project**.

Требования: установленный [GitHub CLI](https://cli.github.com/) и авторизация с правом на проекты:

```bash
gh auth login
gh auth refresh -s project          # доступ к GitHub Projects
```

Запуск:

```bash
chmod +x create_issues.sh
# посмотреть, что будет создано, ничего не отправляя:
DRY_RUN=1 ./create_issues.sh
# создать issues (и добавить в проект с названием "@Fi44er's untitled project"):
REPO=Fi44er/synthcity PROJECT="@Fi44er's untitled project" ./create_issues.sh
# создать только одну фазу:
ONLY_MILESTONE="M0" ./create_issues.sh
```

После выполнения:

1. Откройте проект → все issues будут в колонке **Backlog** (workflow *Item added → Backlog*).
2. Перетащите **5–7 карточек фазы M0** (T001–T018, начиная с P0) в **Ready**.
3. Заполните поля *Priority/Size* (можно по labels: во вкладке Table выделите столбец и вставьте значения).
4. Берите верхнюю карточку из **Ready** в **In progress** — и вперёд.

> Номера issues на GitHub (`#1`, `#2`…) назначаются автоматически. Ссылки между карточками сделаны по ключам `T0xx` в заголовках,
> поэтому порядок номеров не важен: ищите зависимость через поиск по `[T046]`.
