# SynthCity: Спецификация Геопространственного Окружения

Данный документ описывает архитектуру и план реализации статических слоев города (здания, парки, инфраструктура) для обеспечения визуализации симуляции на фронтенде.

## 1. Общий план реализации

Для того чтобы превратить сырые данные OpenStreetMap (.osm.pbf) в интерактивную карту, необходимо реализовать следующий конвейер данных:

### Шаг 1: Расширение парсинга (Enrichment)
Помимо дорожного графа, парсер должен извлекать следующие объекты:
*   **Здания:** Объекты `Way` и `Relation` с тегом `building=*`. Сбор метаданных об этажности (`building:levels`).
*   **Зеленые зоны:** Теги `leisure=park`, `landuse=forest`, `natural=wood`.
*   **Точечная инфраструктура:** Узлы `Node` с тегами `highway=traffic_signals` (светофоры) и `highway=crossing` (пешеходные переходы).

### Шаг 2: Обработка сложных геометрий (Multipolygons)
Особое внимание уделяется объектам типа `Relation` (Multipolygon):
*   **Роли (Roles):** Необходимо корректно разделять контуры на `outer` (внешняя граница объекта) и `inner` (дырки внутри объекта, например, внутренний двор здания или озеро в парке).
*   **Сшивка (Stitching):** Сегменты путей в PBF могут идти не по порядку. Требуется алгоритм стыковки узлов для формирования замкнутых колец.

### Шаг 3: Стратегия хранения
*   **Runtime (RAM):** Дорожный граф остается в оперативной памяти для расчетов пути.
*   **Хранилище (PostgreSQL + PostGIS):** Статическое окружение (тысячи зданий и парков) рекомендуется хранить в БД с поддержкой гео-запросов. Это позволит фронтенду запрашивать данные только для текущей области видимости (Bounding Box).

### Шаг 4: API и визуализация
*   **Формат:** Данные отдаются в формате **GeoJSON** (`FeatureCollection`).
*   **Динамическая связь:** Каждый статический объект должен сохранять свой оригинальный `OSM_ID`. Это позволит связать статическое изображение светофора на карте с его динамическим состоянием, приходящим через WebSockets.

## 2. Технологический стек

Для реализации рекомендуется связка библиотек на Go:

| Библиотека | Роль | Описание |
| :--- | :--- | :--- |
| **github.com/qedus/osmpbf** | Low-level Reader | Экстремально быстрое чтение сырых байтов из PBF-файла. |
| **github.com/paulmach/orb** | Geometry Engine | "Золотой стандарт" ГИС на Go. Создание полигонов, расчет центроидов и упрощение линий. |
| **orb/geojson** | Serializer | Встроенный инструмент для мгновенной генерации валидного GeoJSON. |

**Совместимость:** Эти библиотеки идеально дополняют друг друга. `osmpbf` поставляет сырые данные, а `orb` структурирует их в геометрию, пригодную для фронтенда.

## 3. Спецификация GeoJSON (Пример ответа)

Бэкенд должен формировать ответ, содержащий все типы объектов. В GeoJSON координаты всегда передаются в порядке `[Долгота, Широта]`.

```json
{
  "type": "FeatureCollection",
  "features": [
    {
      "type": "Feature",
      "id": "node/123",
      "geometry": { "type": "Point", "coordinates": [55.1005, 51.7666] },
      "properties": { "type": "traffic_light", "junction_id": 123 }
    },
    {
      "type": "Feature",
      "id": "way/456",
      "geometry": {
        "type": "Polygon",
        "coordinates": [
          [[55.1020, 51.7680], [55.1030, 51.7680], [55.1030, 51.7690], [55.1020, 51.7680]]
        ]
      },
      "properties": { "building": "apartments", "levels": "9" }
    },
    {
      "type": "Feature",
      "id": "rel/789",
      "geometry": {
        "type": "MultiPolygon",
        "coordinates": [[
          [[55.11, 51.77], [55.12, 51.77], [55.12, 51.78], [55.11, 51.77]],
          [[55.111, 51.771], [55.112, 51.771], [55.112, 51.772], [55.111, 51.771]]
        ]]
      },
      "properties": { "leisure": "park", "name": "Central Park" }
    }
  ]
}
